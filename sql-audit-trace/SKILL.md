# SQL Audit Trace

Extract and validate SQL execution traces from Langfuse observations for business logic compliance auditing.

## Purpose

This skill helps audit agents retrieve, **validate**, and **data-verify** SQL queries generated by AI agents through Langfuse tracing. It provides a structured workflow to:
- Query traces by session ID
- Filter observations containing SQL executions
- Extract SQL file paths and content
- **Validate SQL against business rules** (Steps 1–5, read-only)
- **Execute verified SQL via fais-agent MCP** to obtain ground-truth data (Step 6)
- **Compare agent output against actual query results** for data consistency (Step 7)

**Phase 1 (Steps 1–5)**: Read-only SQL audit — SQL is validated for correctness but **NEVER executed** by the audit agent.  
**Phase 2 (Steps 6–7)**: Data verification — the validated (or corrected) SQL is executed via `mcp__mb_transcation_db__execute_sql`, and the agent's reported numbers are checked against the actual results.

> ⚠️ **完整 output 位置**: Agent 的完整輸出（所有數字、表格、論點）**分佈在 trace 各輪 observation 中**，不集中在最後一個 iteration。Step 7 比對時必須從各輪 observation 讀取 Agent 提及的所有內容，而非只看最後一輪。

> ⚠️ **唯一工具**: 本 skill 是此審計流程的唯一工具。禁止使用 `sessions_history`（無權限）或 `Langfuse skill`（功能不足）替代。

## Prerequisites

- `langfuse-cli` must be installed (available via `npx langfuse-cli`)
- `jq` must be available for JSON processing
- Langfuse API access configured

## Workflow

### Step 0: Langfuse HTTP API 直接查詢（備用方案）

**使用時機**：
- `npx langfuse-cli` 無法安裝或執行失敗
- 需要 session-level metadata（Step 1 不提供）
- 環境中沒有 Node.js / npx

**必要環境變數**（注意：使用 `AGENT_LANGFUSE_*` 前綴，與 Claude Code 自身的 `LANGFUSE_*` 分開）：
```bash
AGENT_LANGFUSE_BASE_URL=http://localhost:3000/   # 自架 instance；cloud 版為 https://cloud.langfuse.com
AGENT_LANGFUSE_PUBLIC_KEY=pk-lf-xxxxxxxxxxxx
AGENT_LANGFUSE_SECRET_KEY=sk-lf-xxxxxxxxxxxx
```

**API 操作集**：

```bash
# 1. 查詢 session 下的所有 traces
curl -s "${AGENT_LANGFUSE_BASE_URL}/api/public/traces?sessionId=${SESSION_ID}&limit=50" \
  -u "${AGENT_LANGFUSE_PUBLIC_KEY}:${AGENT_LANGFUSE_SECRET_KEY}" \
  | jq '[.data[] | {id, name, timestamp, sessionId}]'

# 2. 取得單一 trace 的完整 observations（等同 Step 1 + Step 2 的資料來源）
curl -s "${AGENT_LANGFUSE_BASE_URL}/api/public/traces/${TRACE_ID}" \
  -u "${AGENT_LANGFUSE_PUBLIC_KEY}:${AGENT_LANGFUSE_SECRET_KEY}" \
  | jq '.observations | length'

# 3. 過濾含 SQL 執行的 observations（與 Step 2 的 jq pipeline 邏輯相同）
curl -s "${AGENT_LANGFUSE_BASE_URL}/api/public/observations?traceId=${TRACE_ID}&limit=100" \
  -u "${AGENT_LANGFUSE_PUBLIC_KEY}:${AGENT_LANGFUSE_SECRET_KEY}" \
  | jq '[.data[] | select(.output != null)]'

# 4. 查詢最新 trace（適合「剛跑完，不知道 trace_id」的情境）
curl -s "${AGENT_LANGFUSE_BASE_URL}/api/public/traces?sessionId=${SESSION_ID}&orderBy=timestamp.desc&limit=1" \
  -u "${AGENT_LANGFUSE_PUBLIC_KEY}:${AGENT_LANGFUSE_SECRET_KEY}" \
  | jq '.data[0] | {id, name, timestamp}'
```

取得 `trace_id` 後，再套用 Step 2 的 jq pipeline 處理 observations。

**Step 0 vs Step 1 選擇原則**：
- 優先使用 `npx langfuse-cli`（Step 1）：輸出已格式化，jq pipeline 直接可用
- 退回 HTTP API（Step 0）：CLI 不可用，或需要 session-level metadata 時

### Step 1: Find Traces by Session ID

**ALWAYS start by querying the `langfuse` skill's documentation** to understand trace query patterns.

List all traces for a session:

```bash
npx langfuse-cli api traces list --session-id "<session-id>"
```

### Step 1.5: 驗證原始問題一致性（若呼叫方有提供 original_question）

**目的**：確認 mb_bu_user_agent 交付給 fais-agent 的任務，與使用者原始提問是否一致。

**適用條件**：當呼叫 fais-audit-agent 時，呼叫方（mb_bu_user_agent 或 Claude Code skill）有傳入 `original_question` 參數。

**執行步驟**：

1. 取得 session 中第一個 trace 的 input（即 fais-agent 實際接收到的任務訊息）：

```bash
# 取得 session 下的第一個 trace（時間最早）
npx langfuse-cli api traces list --session-id "<session-id>" | \
  jq '[.data[] | {id, name, timestamp, input}] | sort_by(.timestamp) | .[0]'
```

若 input 欄位不在 traces list，改從 trace 詳細取得：

```bash
# 取得最早 trace 的完整 input
npx langfuse-cli api traces get "<first-trace-id>" | jq '{id, name, input}'
```

2. 比對兩者差異：

| 比對項目 | 說明 |
|---------|------|
| `original_question` | mb_bu_user_agent 轉達的原始問題（呼叫方傳入） |
| fais-agent trace input | fais-agent 在 Langfuse 中實際收到的任務文字 |

3. 判斷結果：

> **判斷原則**：使用者提問通常是簡述；fais-agent 根據領域知識、前後文、知識庫補強後的任務描述**必然更詳細**，這是正常且預期的行為。判斷重點只有一個：**核心需求是否一致**，而非文字是否相同。

- **✅ 一致**：核心需求一致，繼續 Step 2。以下情況均屬「一致」，**不需標記 Warning**：
  - fais-agent 展開了 original_question 的縮寫或簡述（如「MOM 分析」→ 明確說明比較月份）
  - fais-agent 根據前後文補充了預設維度（如加入 territory、時間範圍）
  - fais-agent 增加了方法論說明（如說明會讀哪些知識庫文件）
  - 格式差異（換行、前置說明文字、語言風格）

- **⚠️ 部分差異**：fais-agent 在核心需求上有**縮小範圍**、**轉移重點**、或**遺漏 original_question 明確指定的條件** → 在報告中標記 `🟡 Warning: 問題理解可能有偏差`，說明具體差異，繼續 Step 2

- **❌ 不一致**：fais-agent 答了一個**實質上不同的問題**（territory 搞錯、時間範圍完全不同、指標對象改變）→ 在報告中標記 `🔴 Critical: 問題轉達不一致`，說明差異內容，繼續 Step 2（此 Critical 不計入 75% 門檻的 SQL PASS 率）

**輸出（加入最終審查總表的開頭）**：

```markdown
## 🔍 原始問題一致性驗證

- **original_question（mb_bu_user_agent 傳入）**：
  > {original_question}

- **fais-agent 實際收到（trace input）**：
  > {trace_input}

- **驗證結果**：✅ 一致 / ⚠️ 部分差異 / ❌ 不一致
- **差異說明**：{若有差異，說明具體不同之處；若一致則填「無」}
```

> **注意**：若呼叫方未提供 `original_question`，跳過此步驟，不影響後續流程。

### Step 2: Extract SQL-Related Observations (Required)

**CRITICAL**: You MUST use this jq pipeline to filter observations. This prevents data truncation and identifies observations containing SQL executions.

The pipeline filters for observations that contain:
- `thinking` content (reasoning about SQL)
- `exec` tool calls (actual SQL execution commands)

```bash
npx langfuse-cli api traces get "<trace-id>" | jq '
  [
    .observations[]
    | select(
        (.output | objects | .ASSISTANT_OUTPUT.content // []) as $c
        | ($c | any(.type == "thinking"))
          or ($c | any(.type == "toolCall" and .name == "exec"))
      )
    | {
        observation_id: .id,
        node_name: .name,
        extracted_data: [
          (.output.ASSISTANT_OUTPUT.content // [])[] |
          if .type == "thinking" then
            { type: .type, value: .thinking }
          elif (.type == "toolCall" and .name == "exec") then
            { type: .type, tool_name: .name, command: .arguments?.command }
          else empty end
        ]
      }
  ]
  | sort_by(.node_name | match("[0-9]+") | .string | tonumber)
'
```

**Pipeline Breakdown**:

1. **Select Filter**: Keeps only observations with `thinking` OR `exec` tool calls
2. **Extract Fields**:
   - `observation_id`: Unique identifier for the observation
   - `node_name`: Agent node name (e.g., "node_1", "node_2")
   - `extracted_data`: Array of thinking values and exec commands
3. **Sort**: Orders by node number for chronological viewing

### Step 3: Extract SQL File Paths

**IMPORTANT**: SQL execution commands are wrapped in Python heredoc. You need to extract the SQL file path from the `command` field.

**Common patterns**:

1. **mcporter pattern** (most common):
   ```python
   with open('/tmp/xxxxx.sql', 'r') as f:
   ```

2. **Direct psql pattern** (legacy):
   ```bash
   psql -f /tmp/xxxxx.sql
   ```

**Extraction command**:

```bash
echo '<command-from-jq-output>' | grep -oP "(?<=open\(')[^']+\.sql" | head -1
```

Or use jq to extract directly:

```bash
npx langfuse-cli api traces get "<trace-id>" | jq -r '
  [
    .observations[]
    | select((.output.ASSISTANT_OUTPUT.content // []) | any(.type == "toolCall" and .name == "exec"))
    | .output.ASSISTANT_OUTPUT.content[]
    | select(.type == "toolCall" and .name == "exec")
    | .arguments.command
    | match("/tmp/[^'\"]+\.sql")
    | .string
  ]
  | unique[]
'
```

### Step 4: Read SQL Content

#### Option A: Read from File (Primary Method)

If the SQL file still exists in `/tmp/`:

```bash
read_file "/tmp/<extracted-filename>.sql"
```

#### Option B: Extract from Observations (Fallback Method)

**When to use**: If `/tmp/` files have been cleaned up or are inaccessible.

SQL content is also stored in the `write` tool calls within observations. Extract it directly:

```bash
npx langfuse-cli api traces get "<trace-id>" | jq '
  [
    .observations[]
    | select(
        (.output | objects | .ASSISTANT_OUTPUT.content // []) as $c
        | ($c | any(.type == "thinking"))
          or ($c | any(.type == "toolCall" and .name == "write"))
      )
    | {
        observation_id: .id,
        node_name: .name,
        extracted_data: [
          (.output.ASSISTANT_OUTPUT.content // [])[] |
          if .type == "thinking" then
            { type: .type, value: .thinking }
          elif (.type == "toolCall" and .name == "write") then
            { type: .type, tool_name: .name, path: .arguments?.path, sql: .arguments?.content }
          else empty end
        ]
      }
  ]
  | sort_by(.node_name | match("[0-9]+") | .string | tonumber)
'
```

**What this extracts**:
- `path`: The SQL file path (e.g., `/tmp/3b324448bdfe_acc_cybercafe_chipset.sql`)
- `sql`: The full SQL query content stored in the observation

**Example output**:
```json
{
  "type": "toolCall",
  "tool_name": "write",
  "path": "/tmp/3b324448bdfe_acc_cybercafe_chipset.sql",
  "sql": "SELECT\n  accrual_year_month,\n  chipset,\n  SUM(cybercafe_amount) as total_cybercafe_cn\nFROM ads_sales_wac_gross_profit_acc_monthly_di\nWHERE accrual_year_month = 202501\nGROUP BY accrual_year_month, chipset\nORDER BY total_cybercafe_cn DESC;"
}
```

**Recovery Strategy**:
1. Try Option A first (read from file)
2. If file not found, use Option B (extract from observations)
3. Option B provides complete SQL content even after cleanup

### Step 5: Validate Against Business Rules (Read-Only)

**CRITICAL**: The audit process is **READ-ONLY**. You validate SQL logic but **DO NOT execute queries**.

#### Validation Steps:

1. **Read relevant knowledge base documents — full content, every round, no exceptions**:
   - Before validating ANY round, enumerate every TABLE/VIEW/topic touched across **all** rounds being audited, then cross-check each one against `KNOWLEDGE_INDEX.md`'s classification table. `01.data_overview_for_agent.md` and `02.ads_finance_cn_pct_analysis_monthly_agg_di.md` are mandatory for every audit; `03`/`04`/`05`/`06`/`80` are mandatory whenever their listed trigger conditions match any round.
   - Use the `read` tool on the **full file**, WITHOUT a limit parameter:
     ```bash
     read_file "<knowledge-base-path>/<domain-document>.md"
     ```
   - 🔴 **`cat`/`head`/`tail`/`sed` or any shell command that truncates the file is NOT a substitute for `read_file`** — even if it technically avoids the word "limit parameter", piping through `head -N` truncates the same way and violates this rule. Reading only `KNOWLEDGE_INDEX.md` itself, without then opening the documents it points to, does not satisfy this step either.
   - This applies per audit, not per session — re-read even if a similar audit was done earlier, since knowledge base files can change between runs.

2. **Review SQL content** for business logic compliance:
   - Verify correct table/view usage
   - Check filter conditions match business requirements
   - Validate dimension usage (e.g., territory, product_line)
   - Ensure proper joins and aggregations
   - Check for missing exclusions (e.g., VBU filters)

3. **Generate audit report** with:
   - ✓ Compliant aspects
   - ✗ Issues found
   - Recommendations for improvement

### Step 5.5a: 欄位補充（Phase 2 驗證需求）

在計算 75% 門檻之前，先確認 Phase 2 數據比對所需的欄位是否齊全。

**原則**：
- SQL 未輸出某欄位 → **不可**認定為 🔴 Critical 或 🟡 Warning
- 若該欄位是 Step 7 比對 Agent 輸出所需 → 在執行版本中補充該欄位，標記為 🔵 Augmented

**補充方式**（擇一）：
1. **新增原始欄位**：在 SELECT 末尾追加欄位，如 `net_sale_amount_contribution_pct`
2. **衍生計算欄位**：以 SQL 表達式產生，如：
   ```sql
   ROUND(
     (gross_profit_margin_pct - LAG(gross_profit_margin_pct) OVER (
         PARTITION BY dimension ORDER BY accural_period
     ))
     * LAG(net_sale_amount_contribution_pct) OVER (
         PARTITION BY dimension ORDER BY accural_period
     ) / 100, 2
   ) AS gross_profit_margin_impact
   ```

**補充後**：
- 原 SQL 保持不變（PASS/FAIL 判定不受影響）
- Step 6 執行「補充版 SQL」（原始/修正邏輯 + 追加欄位）
- 審查報告中用 🔵 Augmented 區塊說明補充了哪些欄位及用途

### Step 5.5: 75% 門檻判斷（是否繼續 Step 6）

完成所有輪次的 Step 5 後，計算通過率：

```
PASS 輪次數 / 總輪次數 × 100
```

- **≥ 75%** → 繼續執行 Step 6（執行 Agent 原始/修正 SQL），再進入 Step 7
- **< 75%** → **跳過 Step 6**，說明：
  ```
  FAIL 輪次過多（{PASS}/{Total} = {X}%，未達 75% 門檻），跳過 Step 6（不重新執行 Agent SQL）。
  ```

> ⚠️ **此門檻只決定是否重新執行 Agent 自己的 SQL，不可用來跳過 Step 7**：SQL 審查通過率低只代表「SQL 寫法有風險」，不代表「最終輸出的數字一定錯」——尤其是像 cn_for_gp CASE WHEN 的 guard 子句這類容易被誤判的模式，通過率被拉低不代表 Agent 的報告數字真的有問題。**只有實際比對才能確認數字是否真的受影響**，不比對就直接跳過，使用者永遠無法知道那份報告能不能信。
>
> **Ground Truth 現在以「Reference SQL 語句」的形式傳入（不是預先算好的結果表格）**：呼叫方若已提供基準數據，會在任務描述中附上一段標示為「Ground Truth Reference SQL」的區塊，內含一至多筆已知正確的 SQL 語句（不是查詢結果）。看到這個區塊，代表呼叫方要你**執行這些 SQL**取得基準，而不是要你直接讀取現成數字。
>
> **是否執行 Step 7，判斷依據改為「任務描述中是否有 Ground Truth Reference SQL 區塊」，與 75% 門檻無關**：
> - 若有 → **不論 Agent 自身 SQL 的審查通過率為何，都必須先執行這些 Reference SQL**（見下方 Step 6 的「Reference SQL 執行」），再用其結果做 Step 7 比對。這組 SQL 是呼叫方提供的已知正確基準，跟 Agent 自身 SQL 的審查結果無關，**不受 75% 門檻限制**。
> - 若沒有 Ground Truth Reference SQL，才需要靠「Agent 自身 SQL 的重新執行」（見下方 Step 6 的「Agent SQL 執行」）取得比對基準，此時才受 75% 門檻限制——通過率不足時沒有可信的執行結果可比對，才真正需要跳過 Step 7。
>
> 🔴 **若任務描述裡提到「已提供 Ground Truth」，卻找不到對應的 SQL 語句區塊** → **視為 Ground Truth 傳遞失敗，不可直接判定「呼叫方未提供」而略過 Step 7**。此時必須在最終報告中明確回報「任務指示提及已提供 Ground Truth，但實際的 Reference SQL 語句未能傳遞到本次審查 context，Step 7 無法執行」，並具體列出還缺什麼（而不是自行假設「沒有提供」就悄悄跳過，或用 Agent 報告自身的內部一致性驗算來代替與外部基準的比對）。這是傳遞鏈路的問題，不是規則判斷錯誤，必須讓呼叫方知道要重新傳一次。

### Step 6: Execute SQL via fais-agent MCP

Step 6 現在有兩種獨立的 SQL 來源，**觸發條件不同，互不影響**：

**6a. Reference SQL 執行（Ground Truth 來源，不受 75% 門檻限制）**
- **觸發條件**：任務描述中有「Ground Truth Reference SQL」區塊
- 逐筆執行區塊內的每一筆 SQL，**原樣執行，不修改**（這些是呼叫方已驗證正確的基準查詢，不是待審查對象）
- 執行結果即為 Step 7 的比對基準

> 🔴 **禁止以「token 預算」「篇幅限制」「查詢複雜」等理由，自行決定不執行 Reference SQL 並把 Step 6-7 延後成「後續審計階段」**：任務描述已明確指示「無需暫停確認，自動完成完整 Step 0–7」，這是一次性、無人值守的自動化流程——呼叫方不會再回來看你的訊息並回答「要不要繼續」，把任務標記為「待後續」或反問呼叫方「您希望我繼續執行嗎？」等同於**任務沒有完成**，而不是「已完成一部分、其餘待補」。真實發生過的案例：一個 agent 收到全部 4 筆 Reference SQL、SQL 審查也 100% PASS，卻以「token budget 限制」為由完全不執行任何一筆，只憑「SQL 審查通過，可預期數字一致」的推測收尾，並停下來問使用者——這跟另外兩個同時受測、確實把全部或大部分 Reference SQL 執行完的 agent 形成鮮明對比，證明「執行不完」通常是選擇，不是真的做不到。
>
> **正確做法**：若真的評估 4 筆 Reference SQL 執行量過大，**優先精簡的是你自己輸出報告的篇幅**（例如省略部分中間過程說明、Step 5 逐輪審查用表格取代長篇敘述），而不是省略 Reference SQL 本身的執行——Reference SQL 執行結果是 Step 7 唯一的比對基準，沒有它，整份審查報告的「數據一致性」結論就是空話。若時間/資源真的不足以執行全部 4 筆，**至少完整執行並比對其中幾筆**（例如 Territory + ACC business_nature 這兩個最關鍵的層級），並在報告中明確寫「因篇幅考量，Chipset 層級 Reference SQL 未執行，其餘已完整比對」——這是**部分完成 + 誠實說明**，跟「全部不執行 + 問使用者」是完全不同的結果。

**6b. Agent 自身 SQL 執行（無 Ground Truth 時的備用基準，受 75% 門檻限制）**
- **觸發條件**：SQL 審查通過率 ≥ 75%，**且**沒有 Ground Truth Reference SQL 可用
- If the SQL **PASS**ed audit → execute the **original SQL** as-is
- If the SQL **FAIL**ed audit → execute the **corrected SQL** from the audit report's「修正建議 SQL」section

**Execution method（兩者皆適用）** — use the MCP tool directly (no bash, no mcporter):

```
mcp__mb_transcation_db__execute_sql(sql = "<reference-or-validated-or-corrected-sql>")
```

**Rules**:
- Execute **each SQL round** separately; do not merge multiple queries
- 執行 Reference SQL 與 Agent 自身 SQL 時，在報告中標明每筆結果的來源（`reference` 或 `agent-original`/`agent-corrected`），避免比對時混淆基準來源
- Record which version was executed: `original` or `corrected`
- Store the raw result set for use in Step 7

### Step 7: Compare Agent Output Against Actual Data

**觸發條件（任一成立即執行，兩者不需同時滿足）**：
1. 呼叫方已提供 Ground Truth → **一律執行**，不受 75% 門檻限制，直接用 Ground Truth 當比對基準
2. 未提供 Ground Truth，但 Step 5.5 通過率 ≥ 75% → 用 Step 6 執行結果當比對基準

若兩者皆不成立（未提供 Ground Truth，且通過率 < 75%）→ 才停止，僅輸出 SQL 審查報告總表並說明「無 Ground Truth 且 FAIL 輪次過多，無可信基準可比對，請先修正 SQL 後重新審查」。

After obtaining all query results (或已提供的 Ground Truth)，produce an **Agent vs Table** comparison report.

**Comparison rules**:
- ACC = CHN（alias equivalence）
- EEMEA = EAST EURP（alias equivalence）
- 若沒特別說明是 Total，通常整體指的是 CH+SI
- 四捨五入誤差（±1 on rounded integers, ±0.1% on pct）認定為一致，但必須註記
- ✅ = 一致；❌ = 不一致
- LLM 未提及的項目，若其他來源一致，認定為一致

**GP% 貢獻度驗算公式**（用於比對 Agent 輸出的「影響整體GP%」數字）：
```
對整體GP%的影響 = ΔGP%_地區 × 前期 net_sale_amount_contribution_pct_地區 / 100
```
- ΔGP%_地區 = 當期GP% − 前期GP%
- 前期淨銷售佔比 = 使用前期（較早期間）的 `net_sale_amount_contribution_pct`（分母為 CH+SI）
- ⚠️ 不可用 `net_revenue_contribution_pct`（分母為 Total，且是淨營收比）

**Output format**（每次執行必須產出）：

```markdown

- EEMEA = EAST EURP
- 其中沒特別說明是 Total，通常整體指的是 CH+SI，誤差若是四捨五入造成，認定為一致，但要註記
- GP% 貢獻度計算公式說明:
    對整體GP%的影響 = ΔGP%_地區 × 前期淨銷售佔比(net_sale_amount_contribution_pct) / 100
    其中：
    - ΔGP%_地區 = 該地區當期GP% - 該地區前期GP%
    - 前期淨銷售佔比 = 前期 net_sale_amount / CH+SI 前期 net_sale_amount × 100（使用前期值）
    - 除以 100 是因為兩個百分比相乘需要轉換為小數
```

## Common Use Cases

1. **Post-execution SQL review**: Audit what SQL was generated after an agent completes a task (read-only)
2. **Compliance checking**: Verify generated SQL follows data access policies without execution
3. **Debugging**: Trace SQL generation logic through thinking + execution pairs
4. **Performance analysis**: Identify SQL patterns and potential optimization opportunities
5. **Pre-deployment validation**: Review SQL before allowing production execution

## Notes

- The trace ID can be obtained from previous `traces list` output
- SQL temp files are typically stored in `/tmp/` with hash-prefixed names (e.g., `3b324448bdfe_acc_cybercafe_chipset.sql`)
- **SQL execution is wrapped in Python heredoc** using mcporter + execute_sql, not direct psql commands
- **Audit is READ-ONLY**: Validate SQL logic but never execute queries
- The `or` operator in the filter ensures both SQL planning (thinking) and execution (exec) are captured
- Multiple SQL files may be executed in a single observation (iterate through all toolCall entries)
- **Fallback mechanism**: If `/tmp/` files are cleaned, SQL content can be extracted from `write` tool calls in observations (see Step 4 Option B)
- SQL content is preserved in Langfuse observations even after temporary files are deleted
